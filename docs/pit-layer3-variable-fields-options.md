# 層3: 車種・チューニング・レギュレーションで変動する項目のUI — 3案

これはエージェントが決めてはならない範囲の意思決定である。3案を並べ、
**何を捨てて何を取るか**だけを書く。推奨は付けない。

## 対象となる項目

基本記録タスク（4輪空気圧・気温・ベストラップ・フィーリング）**以外**の、
車両によって存在したりしなかったりする項目。

| 項目 | 変動の理由 |
|---|---|
| 目標空気圧（前/後） | 車重・タイヤ銘柄・レギュレーションで違う。緑/橙の判定根拠になる |
| ダンパー減衰（クリック数） | ダンパー銘柄で段数も向きも違う（8段/32段、締める向きが逆の製品もある） |
| スプリングレート | kgf/mm と N/mm が混在する |
| 車高・キャンバー・トー・キャスター | 調整機構の有無が車両ごと |
| ブレーキバランス・エアロ・ECU/ブースト | 装備車のみ。レギュレーションで禁止される場合もある |
| タイヤセット管理 | シリーズによって義務/不要が分かれる |

現状は `VehicleSetupConfig`（`src/types/vehicle.ts:133`）に
「この車で入力できる項目」を定義し、`DynamicSetupTab` が描画している。
目標空気圧だけはこの仕組みの外にあり、自由な数値2つで持っている。

---

## 案A: 車両プロファイル先出し（現行方式の延長）

車両登録時に「この車で変えられる項目」と単位・範囲・段数を定義しておき、
記録画面はその定義に沿った入力欄だけを出す。

**取るもの**
- 記録時に見える項目が最小になる。存在しない項目は最初から出ない
- 単位・段数が車両ごとに確定するので、保存データの列が安定する。
  **後から集計・比較・販売できるデータになる**（事業方針の中核）
- 目標空気圧も車両プロファイルに置けば、緑/橙の判定根拠が明示される

**捨てるもの**
- 初回の登録コストが高い。「まず車両を登録してください」が記録の前に立つ
- ダンパーを組み替えた・シリーズが変わった、のたびにプロファイル保守が要る
- 借りた車・他人の車での記録が重い

---

## 案B: 記録は自由入力、構造化はあと（記録取りこぼしゼロ優先）

走行直後は「変えたこと」を1行ずつ自由に書くだけにする
（例: `リア減衰 8→10`、`フロント車高 -3mm`）。
構造化はピットを離れたあとに、アプリが候補を出して行う。

**取るもの**
- 事前準備なしで書ける。車両プロファイルが無くても記録が始まる
- 走行直後の「言葉にしやすい形」で残せるので、書き漏らしが最も少ない
- 借りた車・初めての車でも同じ手順

**捨てるもの**
- その場では構造化されない。比較ビュー・チャートにすぐ乗らない
- 表記ゆれが必ず出る（`リア減衰` / `Rダンパー` / `rear damper`）
- **あとで正規化する工程を誰かがやる前提**。やらなければ検索も集計もできない
  死蔵データになり、データを売る事業とは相性が悪い

---

## 案C: 前回との差分だけを聞く（変更点ドリブン）

前回のセットアップを基準に「今回いじった項目」だけをリストから選ばせ、
値を入れる。触っていない項目は前回値を継承する。

**取るもの**
- サーキットでの実作業（1〜2項目だけ触る）と操作が一致する。入力量が最小
- 「何を変えたら何が変わったか」が記録の構造そのものになる。
  セットアップ探索という本来の目的に最も近い形で残る
- 車両プロファイルが薄くても、前回さえあれば動く

**捨てるもの**
- 初回セッションでは効かない（比較対象が無い）。初回だけ別導線が要る
- 継承値と実測値を保存側で区別する必要がある。区別せず継承値を実測として
  保存すると**偽データの混入**になり、事業上の欠陥として扱う方針に反する
- 「前回」の定義が要る（同じ車？ 同じサーキット？ 同じタイヤ？）。
  ここを間違えると無関係な値を引き継ぐ

---

## 決める必要がある点

1. どの案を採るか（併用も可。例: 目標空気圧だけA、調整項目はC）
2. 案Cを採る場合、「前回」をどの条件で一致とみなすか
3. 継承値・自動取得値・実測値を保存データ上でどう区別するか
   （現状 `autoWeather` の取得値には出所を持たせていない。要設計）
4. 目標空気圧を車両プロファイルへ移すか、セッションごとに入れるか
